# Feature specs: Employee address change

Define what an employee is asked when they report a change of address, under which conditions, and who needs the information.


These feature specs describe **what** is needed and **why**, with acceptance
criteria and concrete examples. They contain no technical decisions: how to
build it is up to engineering. Every statement is traceable to a source quote,
a product-owner guideline (G-) or a product decision (D-).

## Features

| # | Feature | Goal | Stories | Open questions |
|---|---|---|---|---|
| 1 | [Capture the new address](features/FEAT-01-new-address.md) | HR gets the complete new address of a moving employee so master data is updated and documents such as payslips reach the right address. | 2 | 1 |
| 2 | [Date from which the new address applies](features/FEAT-02-valid-from.md) | HR knows from which date to use the new address, in particular for the payslips sent out on the 25th, and still accepts moves reported late within a fixed window. | 2 | 2 |
| 3 | [Inform payroll about moves abroad](features/FEAT-03-payroll-move-abroad.md) | Payroll is reliably informed whenever an employee moves abroad, so it can check whether source tax applies, and is not involved in moves within Switzerland. | 2 | 2 |
| 4 | [Capture a change of canton for the tax office](features/FEAT-04-canton-change.md) | When an employee moves to a different Swiss canton, HR gets the new canton and can pass the change to the tax office, without asking for the canton in any other case. | 3 | 1 |

## How to read a feature spec
- **User stories** (`US-x.y`): who wants what and why, with priority.
- **Acceptance criteria** (`AC-x.y.z`): Given / When / Then in business
  language. Where a criterion involves conditions or rules, an **examples**
  table gives concrete cases – real cases from the sources first. ✅ in the
  "Checked" column means the pipeline executed the example against the
  consolidated business rules and it holds.
- **Information needed**: what, when asked, when required, depends on, who
  needs it – for every piece of information the feature owns.
- **Business rules**: plain-language rules with decision tables.
- **Evidence**: the source quotes behind the feature.
- The header of each file (between `---` lines) is traceability metadata for
  tools (e.g. syncing to an issue tracker), not a data model.
